## Goal (roadmap.md Phase 5)

Queue system เต็มรูปแบบตาม queue.md — **DoD:** ทุก operation (add/addNext/remove/
move/clear/shuffle/unshuffle/repeat) ทำงาน + **previous ถูกต้องแม้ shuffle** +
**restart backend แล้ว queue กลับมา**

## Scope

- `packages/shared/queueLogic` — pure model (QueueItem มี id ต่อชิ้น รองรับ track ซ้ำ)
  - advance/previous/shuffle/unshuffle + unit tests ครบ (ตัวอย่าง A→D→B→C, repeat
    off/one/all × skip/previous/ended, unshuffle หลัง mutate)
- QueueService (ผูกเข้า PlayerService ต่อ user — state เดียวกันกัน diverge) + REST
  api.md §5: GET /queue, POST /queue/tracks, POST /queue/tracks/next,
  PATCH /queue/items/:id/move, DELETE /queue/items/:id, DELETE /queue?scope= +
  PATCH /player/shuffle (endpoint #18) + skip/previous ใช้ queue จริง
- Persistence: queue_snapshots + queue_items ทุก mutation; โหลดคืนตอน restart
  (restore เป็น PAUSED ไม่ auto-play — player.md #7)
- Frontend: queueStore + QueuePanel (upcoming/history, remove, move, clear) +
  handleEnded → advance ผ่าน server

## การตัดสินใจ (tensions จาก queue.md vs api.md)

1. **remove current** → 409 `ITEM_IS_CURRENT` (ตาม api.md:87 ให้ client ใช้ skip — เหตุผล
   "กัน ambiguity" ชัดกว่าข้อความ "remove current = skip" ใน queue.md §2)
2. **previous restart >3 s** → ยังตัดสินฝั่ง client (บทเรียน Phase 4: server ไม่รู้
   position จนกว่าจะมี WS Phase 7); server ทำหน้าที่ pop history เท่านั้น
3. **history ใน queue_items** → kind='hist' position 0..99 (0 = เล่นล่าสุด, ใหม่→เก่า)
   เขียนทับทั้งชุดทุก mutation (cap 100) — ง่ายและถูกต้องกว่า delta ordering
4. **QueueStateDTO** อัปเกรดเป็น `QueueItemDTO { id, track }` ตาม api.md §1 (ตอนนี้
   Phase 4 ใช้ TrackDTO ตรง ๆ — remove/move by id ต้องมี id ต่อชิ้น)
5. **autoplay refill (radio/RecommendationService)** → Phase 11; Phase 5 advance เมื่อ
   upcoming ว่าง → ENDED (คง flag autoplay ไว้ใน settings)
